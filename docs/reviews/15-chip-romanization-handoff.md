## What this feature is
In the Scan tab, each syllable "chip" under a scanned verse should show its Roman/Devanagari spelling using the *correct*, verified text (from `data/exercises_verified.json` / `ghalib_extended.json` / `mir_extended.json`) rather than a crude letter-substitution fallback that drops Urdu's unwritten short vowels (producing things like `ḥt` instead of `ḥat`).

Code (all in `original_base.html`, never edit `index.html` directly — it's generated by `scripts/build_app.py`):
- `romanNuclei`, `romanConsonantUnits`, `syllabifyRoman(word,n)` (~line 990–1010): splits a word's correct Roman spelling into exactly N syllable pieces by vowel position + a consonant-cluster rule (single intervocalic consonant → following syllable; 2+ → first stays with preceding, rest go to following; digraphs kh/gh/bh/ph/th/dh/ḍh/ṛh/chh/jh/ḳh/ġh treated as one unit, never split).
- `wordRomanMap(lineObj,r)` (~line 1013): aligns the scanner's per-word tokenization (`r.words`, which may graft multiple Urdu tokens into one scanner "word") against `lineObj.ro.split(/\s+/)` with a single running pointer; returns null (whole line falls back) if the total token count doesn't reconcile.
- `chipRomanOverrides(syl,li)` (~line 1027): per scanner-word, counts syllables and calls `syllabifyRoman`, assigns pieces in order.
- `chipHTML(s,i,li,override)` / `chipsHTML(syl,feet,li)`: use the override when present (`currentScript==='ro'` only right now — Devanagari/`hi` still always uses the old crude method), else fall back to `translitText(s.text,cs)` exactly as before this feature existed. Fallback is always safe — never produces new garbage, just doesn't improve.

## Diagnosis of the remaining problem (Opus agent, read-only audit, evidence-based — not speculation)
Ran the real `scanMirExtInStudio(4)` path (the actual "Scan Ghazal" button) in a Node vm sandbox with `currentScript='ro'`, and separately audited the **entire corpus**: 6,201 lines, 88,608 chips. Confirmed: **only 53.7% of chips get the improved spelling; the rest correctly fall back (safe, just incomplete)** — not random, not stale, not order-dependent. Three specific, independently-confirmed causes:

**A. Any hyphen in a word's correct Roman spelling drops the *entire line*.** `wordRomanMap` (line 1013) splits `lineObj.ro` on `/\s+/` only — a hyphenated compound (`āshuftah-sarī`, `tāj-varī`, `nauḥah-garī`, `be-dād-garī`, `dast-nigar`, `kār-gah-e`) is one Roman token but corresponds to what the alignment counts as 2 Urdu words, so the final pointer check fails and the *whole line* (not just that word) falls back. **1,913 of 6,201 lines (31%) get zero improvement**; 1,866 of those have a hyphen in `ro`. (The other 47: future-tense splits like `deñge` vs `دیں گے`, plus one bad data row `mir90:18`.)
  - Fix idea: split `ro` on spaces *and* hyphens (keep izafat `-e`/`-o` attached to the preceding piece), and make the alignment fail **per word**, not per line, so one bad word doesn't sink the rest.

**B. Any word ending in a closed syllable always fails — the biggest cause (5,384 words).** Urdu/Persian prosody counts a final consonant (after a long vowel, or a doubled consonant) as its own metrical beat: āfāq = ā·fā·q, kaun = kau·n, rāh, asbāb, rang, ashk, sāñs, kām, yār. `syllabifyRoman` (line 996) only counts vowel nuclei, so `nuclei.length !== n` and it returns null — there's no way to produce a vowel-less final piece. This is what produced the visible garbage in the screenshot: `[ko][n]` for kaun, `[īāñ]` for yāñ, and one case (`آئینے`/L11) where a stray Urdu letter leaks into otherwise-Roman text.
  - Fix idea: when `n === nuclei.length + 1`, split the trailing consonant run off as its own final piece (still respecting the digraph rule).

**C. Hyphens are miscounted as consonants in the cluster rule**, so izafat splits land one letter off (`mausam-e` → `mau·sam·-e` instead of `mau·sa·me`; also `dāvar-e`, `tah-e`, `qīq-e`, `rāġh-e`, `kabk-e`).
  - Fix idea: don't count `-` as a consonant unit in `romanConsonantUnits`; attach it to the following piece.

**Ruled out** (don't re-investigate): stale build, the hidden `#studioResults` div (dead but harmless — `runStudioScan()` still runs and rebuilds ~190KB into it every scan, a real but separate perf issue, low priority), cross-line state leakage, mid-line word-count misalignment that "cancels out" in the total check, anything else trapped in the scanner IIFE. The "se" that looks like it bleeds into the wrong foot box in the screenshot is **correct prosody** (feet cross word boundaries), not a bug.
