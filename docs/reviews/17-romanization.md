# 17 — Romanization: PDF conventions, Pue-parser audit, and a better OOV predictor

Scope: everything here lives in `translit-lab/` (code + generated artifacts) plus this doc.
Nothing in `src/`, `scripts/`, `tests/`, `data/`, `pritchett_scripts/`, `index.html`, or
`package.json` was touched. Run scripts with `uv run python translit-lab/<script>.py` from
the repo root (or from inside `translit-lab/` as shown below); the corpus reads and node
probes are read-only.

## 1. The problem, restated precisely

The app has two paths to Roman:

- **Exact path**: Pritchett-ASCII → Sean Pue's graph parser (`pritchett_scripts/*.js`,
  bundled into the runtime the build script calls `PUE_PARSER`) → Urdu / Devanagari / Roman.
  This is deterministic and, as far as I can tell (§3), bug-free *given well-formed ASCII in
  the conventions this corpus actually uses*.
- **Lossy fallback**: a typed Urdu-script word goes through a word dictionary built from the
  corpora, and on a miss, through `urduToRoman()` — a plain per-character map with no
  context — in `src/js/05-translit-helpers.js`. Urdu script doesn't write short vowels,
  iẓāfat, or tashdīd, so this fallback is wrong most of the time on words it hasn't seen
  verbatim before. That's the gap this work targets.

## 2. The PDF's conventions vs. what Pritchett/Pue's output actually does

I read `Urdu Romanization.pdf` (a copy of the standard Pritchett-style romanization rules,
24 numbered rules) and cross-checked each rule against the parser's real behavior by running
it directly (`node -e` loading `pritchett_scripts/{urdu,devanagari,diacritics}_parser_data.js`
+ `ghalib.js`, exactly the way `scripts/build_app.py` does for `FAMS`) and against the four
ground-truth corpora, whose `ro`/`ur`/`hi` fields were themselves generated by this same
parser (confirmed in §3 — 0/7333 lines disagree, so the corpora aren't an independent check
of the parser, just of convention drift).

Rule-by-rule, where the app's actual usage agrees or diverges from the PDF:

| Rule | PDF says | App/corpus practice | Verdict |
|---|---|---|---|
| 3 (ا → ā) | alif after consonant = ā, alif maqṣūrah (superscript ی) = á | matches; `sh-e` etc. all render correctly | agrees |
| 6 (ن vs ں) | dotted ن → *n*, undotted ں → *n̲* (distinguished only by an underline in print) | app/corpus use plain `n` vs `;N`/`;n` (nasal marker) — a *stronger*, ASCII-safe distinction than the PDF's underline, not a weaker one | improves on PDF for a plain-text medium |
| 7c (و = ō) | e.g. *dōst* | corpus renders long ō as `o` (`dost`), same | agrees |
| 8 (final ہ retained as *h*) | *guldastah* | matches (`;Gam-;xvaar-e` etc. keep final h) | agrees |
| **17 (iẓāfat)** | **-i** after a consonant-final muzāf, **-yi** after a vowel/silent-ہ-final muzāf | the app/corpus use **-e uniformly**, regardless of what the muzāf ends in (e.g. `dast-e`, `naaz-e`, never `dast-i`) | **deliberate simplification**, and it's the right call — see §3, the parser's graph doesn't actually support `-i`/`-yi` correctly, so keeping to `-e` sidesteps a real bug |
| 18 (Arabic ال) | assimilates in *pronunciation* to sun letters but keeps `ال` in *spelling* | not exercised anywhere in the corpora (no Arabic ال loanwords with sun-letter assimilation appear); parser mishandles it when tried directly (§3) | untested corner, matches PDF only for moon letters |
| 19 (و = "o" conjunction vs "va" otherwise) | -o- for a tight phrase pair, va elsewhere | corpus only ever uses the `-o-` form (`((ajz-o-qaalib`, `tang-o-;zauq`); never saw a bare "va" | consistent subset of PDF, untested for "va" |
| 23 (short vowels supplied "from a dictionary") | explicit acknowledgment that Urdu script alone can't determine them | this is exactly the app's fallback-accuracy problem — the PDF calls out the same gap this task addresses | confirms the problem statement |

**Recommendation:** keep Pritchett-with-`-e`-uniform as the default (matches existing
corpus convention and avoids a real parser gap, see below); it's not worth introducing the
PDF's strict `-i`/`-yi` split as a user-facing option unless the parser's graph is extended
to support it (not attempted here — out of scope, flagged for someone touching
`pritchett_scripts/`).

## 3. Pue-parser audit

Ran the actual parser (not a re-implementation) via node against (a) every corpus line's
`ascii` field, and (b) a battery of hand-built strings targeting nasal ñ, ʿayn, hamza,
iẓāfat, do-chashmī he aspirates, tashdīd, Arabic ال.

**(a) Regression check against corpora**: 7333/7333 lines' `p_di.parse(ascii)` output match
the stored `ro` exactly, 0 mismatches. So for every ASCII form this app's corpora actually
use, the parser is faithful (unsurprising since the corpora were generated by it, but it does
confirm there's no drift between the checked-in data and the checked-in parser).

**(b) Targeted probes found two real gaps**, both in iẓāfat handling, both in the *reverse*
direction (ASCII → Urdu script) rather than in the Roman output the corpora exercise:

1. **`-i` iẓāfat (PDF rule 17a)** is not in the parser's graph. `a;xtar-i.sad-baar` produces
   Urdu `اختر اصد بار` — a spurious literal alif (ا) is inserted as its own word instead of
   the hyphen being absorbed silently. Nothing in the corpora uses this form (the app
   convention sticks to `-e` uniformly, see §2), so this never fires in practice, but it
   would break for any hand-typed ASCII that follows the PDF's stricter rule.
2. **`-yi` iẓāfat (PDF rule 17b)**, needed after a vowel/silent-ہ-ending muzāf — Pritchett's
   own worked example is `malikah-yi Inglistān` → `ملکۀ انگلستان` (a single hamza-topped ہ).
   The parser instead emits `ملکہ یی انگلستان` — literal, separate "یی" letters as if it were
   a new word. Same story: unused in the corpora, real if triggered.

Both are latent, not live bugs — they'd only surface if this project (or a future
predictor) started emitting strict-Pritchett `-i`/`-yi` ASCII instead of the corpus's
`-e`-everywhere convention. Recommendation: don't; keep `-e` uniform, and treat these as
"known gap in `pritchett_scripts/urdu_parser_data.js`'s graph" for whoever next edits that
file (I did not touch it, per scope).

Everything else probed came back correct: nasal ñ (`;N`/`;n`), ʿayn (`((`), hamza in all
three positions (`mu))min`, `bhaa))ii`, `li))e`), do-chashmī-he aspirate digraphs (`bh`, `kh`,
`gh`, ...), tashdīd/gemination (`qavvat`→`qavvat`+doubled و in Urdu, `sayyid`, `makkhii`),
the `-o-` conjunction, and Arabic `ال` for moon letters (`al-qur))aan`). No patch files were
needed since I found no fixable, in-scope bug — see `translit-lab/pue_parser_audit.md` is
*not* a separate file; the findings above are the complete audit (kept in this doc rather
than splitting it, since there's nothing to diff against unused code paths).

## 4. The predictor

Files: `translit-lab/prep_data.py`, `align.py`, `baseline_map.py`, `char_model.py`,
`predictor.py`, `evaluate.py`, `export_js.py`.

**Data prep** (`prep_data.py`): loads all four corpora, strips harakat
(`ً-ٰٟ`) and NFC-normalizes (so Pue's ا+maddah decomposition of آ collapses
back), to simulate typed unvowelled input. Word-aligns each Urdu line against its
Pritchett-ASCII line. The naive alignment (just split both on whitespace) only matches
~24% of lines, because Pritchett's ASCII hyphenates iẓāfat and compounds onto neighbouring
words while Urdu script writes them as separate words. Fix: split each ASCII token on `-`,
then re-merge any resulting bare `e`/`i`/`yi` fragment onto the preceding fragment (unwritten
iẓāfat), while keeping a bare `o` fragment separate (the written و conjunction). That raises
line-level word-count alignment to **~91%** (4581/5035 lines on Ghalib alone were 98.6% before
counting the other corpora); the remainder (mostly a verb written as two Urdu words but one
ASCII word, e.g. `دیں گے` vs `de;Nge`) is dropped rather than guessed at. Split 70/15/15 by
**ghazal id** (not by line) so no stem/word from a test ghazal leaks into training via a
sibling couplet. Output: `translit-lab/data/{train,dev,test}.jsonl` (~38k/9k/9k word pairs).

**Baseline** (`baseline_map.py`): a faithful Python port of the app's actual
`urduToRoman()` + `romanToAscii()` pipeline, so the comparison is against what the app
really does today, not a straw man.

**Approach chosen** (of the three suggested, in order of simplicity): I built (1)
morphological back-off and (3) a character-context statistical model; I did not build a
seq2seq net — a small n-gram/back-off model already closes most of the gap cheaply and
ships as a flat table, matching the "small JS table" integration constraint.

- **Character-context model** (`char_model.py`): learns, per Urdu letter with 1-char
  left/right context, the most frequent true ASCII chunk it corresponds to, backing off
  tri-context → right-bigram → left-bigram → unigram → the existing single-letter map.
  Training signal comes from **forced alignment** (`align.py`): the naive per-character
  baseline output is diffed (via `difflib`) against the true ASCII, and whichever chunk of
  the true string a mismatch maps to is credited to that Urdu character in its 1-char
  context. E.g. for `ستاروں` → `sitaaro;N`, ت in context (س, ا) is credited with emitting
  `it` (recovering the dropped kasra), not just `t`.
- **Morphological back-off** (`predictor.py`): before falling to the character model, strip
  a known inflectional suffix (`وں` oblique plural, `یں`, `ے`, `ی`, `اں`) and check whether
  the bare stem was seen verbatim in training; if so, splice the stem's known ASCII to the
  suffix's ASCII (itself computed via the char model, using the stem's last letter as left
  context — so a known stem plus a productive suffix composes correctly even when the whole
  inflected form was never seen).

## 5. Evaluation

Evaluated only on **OOV words** — Urdu surface forms that never occurred verbatim in
training — since exact-form matches are already handled correctly today by the app's own
corpus dictionary; that's the honest test of whether the new fallback generalizes.

```
=== dev (OOV words: 546 / 9146 total) ===
baseline letter-map : word acc 0.088  CER 0.279
new predictor       : word acc 0.388  CER 0.150
of 498 baseline-wrong OOV words: predictor fixed 173 (34.7%), regressed 9
predictor back-off path usage: {char_model: 439, morph: 107}

=== test (OOV words: 444 / 8749 total) ===
baseline letter-map : word acc 0.083  CER 0.289
new predictor       : word acc 0.374  CER 0.156
of 407 baseline-wrong OOV words: predictor fixed 140 (34.4%), regressed 11
predictor back-off path usage: {morph: 72, char_model: 372}
```

Headline numbers (test split): **word accuracy 8.3% → 37.4%** (4.5x), **character error rate
0.289 → 0.156** (46% relative reduction), and of the baseline's wrong OOV words, **34.4% are
now fixed to an exact match** (many more are closer even when not exact — that's what the CER
drop captures), against an **11-word regression** (2.5% of baseline-wrong cases; new
mistakes, mostly the model overfitting a locally common vowel pattern to a word that needed
a different one — inherent to any lexical-frequency-based approach on ~8k training words).

Worked examples (`urdu | true | baseline | predictor`):

```
ستاروں   sitaaro;N     staaro;n     sitaaro;N    (via dict — seen in training)
جہاں    jahaa;N       jhaa;n       jahaa;N      (via dict)
اور     aur           aor          aur          (via dict)
برسی    barsii        brsii        barasii      (via morph: بر + سی, stem seen)
افسوں   afsuu;N       afso;n       afso;N       (via char_model)
ہاموں   haamuu;N      haamo;n      haamo;N      (via char_model)
پشیماں  pashemaa;N    pshiimaa;n   pashemaa;N   (via char_model)
```

`ستاروں`, `جہاں`, `اور` above are dictionary hits once the model is trained on the full
corpus (as it will be when shipped, §6) — they're shown because they're the exact words
named in the original bug report, and confirm the *fixed* letter-map issues
(اور no longer becomes `aor`; the fallback path itself, exercised on the truly-unseen test
set, is what the accuracy table measures).

**Where it still falls short**: word-initial short vowels the model has never seen in that
exact left/right-character context (e.g. `ستاروں` itself, if genuinely OOV, comes out
`staaro;N` — missing the "si-" — because س at word start followed by ت is ambiguous without
lexical knowledge of the specific root sitārah). This is an inherent limit of a
context-window model without a real morphological analyzer or lexicon of stems; the
dictionary + morphological back-off tiers cover the common case (recurring stems across
ghazals), and the character model is strictly better than the letter map for the residual
unknowns, but it will never fully solve genuinely novel roots. A stem lexicon seeded from
`data/glossary.json` would help further, but that file only has ASCII+meaning, no Urdu
spelling, so using it would require running it forward through the Pue parser first
(cheap, but out of scope for this pass).

## 6. Integration plan

The app is a single offline HTML file with a ~200KB romanization-table budget. Concretely:

1. **Don't ship a duplicate word dictionary.** The app already builds one from the same
   corpora (`KNOWN_VERSES` / the word-dictionary construction in `src/js/05-translit-helpers.js`
   the problem statement describes). Re-shipping it would be redundant weight.
2. **Ship only the new fallback tier**: `translit-lab/urdu_char_fallback.js`, generated by
   `export_js.py`, is the trained char-context table (tri/bi/uni, no dictionary) plus a
   ~40-line decoder (`predictAsciiForUnknownWord`) that mirrors `predictor.py`'s morphological
   back-off + char-model back-off chain. **110KB raw / ~34KB gzip'd** (well under budget;
   GitHub Pages serves gzip'd text by default, so real transfer cost is ~34KB).
3. **Splice it into the existing chain** in `src/js/05-translit-helpers.js`: today it's
   `word dictionary → urduToRoman() letter map`. Change it to
   `word dictionary → predictAsciiForUnknownWord() (using the existing word dictionary as
   its `wordDict` argument) → urduToRoman() letter map` as the final safety net for any
   character the table never saw. The output of `predictAsciiForUnknownWord` is
   Pritchett-ASCII, so it should be run through the *existing* `PUE_PARSER` bundle
   (`window.p_ur.parse` / `p_hi.parse` / `p_di.parse`) rather than displayed directly — that
   keeps Urdu/Devanagari/Roman consistent with each other for the predicted word, instead of
   only fixing Roman and leaving Devanagari on the old letter-by-letter path.
4. **Retraining**: rerun `translit-lab/export_js.py` whenever the corpora grow (new ghazals
   added to `data/*.json`); it's a ~1s script with no external dependencies beyond the
   standard library.
5. Not done here (explicitly out of scope): wiring this into `src/js/05-translit-helpers.js`
   itself, since that file was off-limits for this task.
