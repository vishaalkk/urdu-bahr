## 2. How ghalib.js works, and bugs found
`Parser` builds a token graph once at construction (`get_edges_sorted_by_next_token`, onmatch matrices) — not rebuilt per call, so no per-parse regex/graph rebuild cost. `parse()` tokenizes the input, walks the graph (`descend_node`) matching prev/next-token-class context rules (`match_rule`), and separately applies "onmatch" rules for contextual insertions (izafat, nasalization, etc.).

Issues found reading the code:
- **Silent failure on unknown chars**: unmatched characters just log `'bad character...'` and get skipped (`token_i += 1; continue`) with no signal to the caller. `build_app.py` wraps every `.parse()` call in `try{}catch(e){}`, so failures are silently swallowed twice over.
- **In-place array mutation**: `match_rule` does `rule[PREV_CLASSES].reverse()` on the shared graph-data array on every call. This is a real anti-pattern — empirically harmless today because `to_match` is reversed the same way within the same call (self-corrects), but it's a landmine for any future concurrent or memoized use.
- **Shared closure constants**: `RULE`, `TOKEN`, `PREV_CLASSES`, etc. are outer-closure vars shared across *all* `Parser` instances and get overwritten if `graph.compressed` is set. Harmless today only because the urdu/devanagari/diacritics graphs are all `compressed: true`; would silently corrupt matching if that ever diverged.
- **Cosmetic**: `console.log('parser loaded; len of graph: ' + graph_json)` fires 3× per page load and prints `[object Object]` (string-concatenating an object), not an actual length.

## 3. Critical: direction handling
Pue's native direction is **ASCII → {ur, hi, ro} only** (confirmed via `franpritchett.com/00ghalib/about/txt_translit.html`). `build_app.py` correctly routes Devanagari/Roman input through hand-rolled `devToAscii`/`romanToAscii` and then into the *real* parser (`p_ur`/`p_hi`/`p_di`) — good design.

But Urdu-script input (Studio's novel-input path, `build_app.py:1014-1016`) never touches the parser at all: it goes straight to hand-rolled `urduToDevanagari`/`urduToRoman` (`build_app.py:587-651`, `index.html:1506-1570`), a 1–2 character regex map with **no short-vowel insertion**. Since Urdu script doesn't write short vowels, this direction is inherently lossy — and the app gives no indication of that uncertainty; it just emits confident-looking, often wrong, text.

## 4. Root causes of the 0% ur→hi/ro rate
- **[Critical] Unicode normalization bug.** `exercises_verified.json`'s `ur` field encodes "آ" (long ā) as the *decomposed* sequence U+0627 (bare alef) + U+0653 (combining maddah) — confirmed by codepoint dump — but `singleMap` only has a key for the *precomposed* U+0622. The combining mark falls through to `else { out += ch }` and leaks raw into the output, e.g. "آب" → expected `आब`/`āb`, got `अٓब`/`aٓb`. آ is extremely common, so this alone wrecks nearly every line.
- **[Real bug] multiMap ordering.** Digraph rules (`جھ`, `چھ`, `تھ`, …) run before word-specific overrides (`مجھ`, `تجھ`, `کچھ`, `تھا/تھی/تھے`, `تجھے`) in the same ordered array (`build_app.py:590-595`/`623-628`). `.replace()` runs top-down, so the digraph consumes the substring first — 7 of 15 word-specific rules are dead code. E.g. "مجھ" → expected `मुझ`/`mujh`, got `मझ`/`mjh`.
- **[Inherent, unflagged] Homograph ambiguity.** "کیا" = both "kiyā" (did) and "kyā" (what), identical spelling; the map always emits one fixed reading with no uncertainty signal.
- **Self-consistency caveat.** `exercises_verified.json`'s ur/hi/ro fields were themselves generated by running `ascii` through this same `p_ur`/`p_hi`/`p_di` (`scripts/build_audited_exercises.js:173-183`), so the 100% ASCII-direction score is self-consistency with the generator, not independent ground-truth verification. Still meaningful (proves determinism, no regressions), but "100% audited" overstates independent verification of ur/hi/ro.

## 5. Recommendations, ranked by impact
1. Normalize Unicode (`str.normalize('NFC')`) at the top of `urduToDevanagari`/`urduToRoman` (`build_app.py:587,620`) and on `devToAscii` input. One-line fix, resolves the majority of ur→hi/ro failures.
2. Route Urdu-script Studio input through the real parser (build an ur→ascii inverse) instead of the hand map; at minimum, label hand-map output as approximate in the UI, since short-vowel loss is unavoidable without a lexicon.
3. Fix `multiMap` ordering in `build_app.py:590-595/623-628` (word-specific entries before digraphs, or `\b`-anchor them) so the dead overrides actually fire.
4. Relabel the "100% audited" claim in `PROJECT_HANDOFF.md` for ur/hi/ro as "parser-generated and internally consistent" rather than independently audited.
5. Add an Apache-2.0 LICENSE/NOTICE file for `pritchett_scripts/` (© 2015 Michigan State University, from `github.com/seanpue/ghalib.js`), referenced near the existing bibliography citation.
6. Document (don't fork upstream) the shared-closure-var and in-place-`.reverse()` landmines in `ghalib.js` — harmless today, worth a warning comment for future maintainers.
